# moc 空会话个位数 MiB 可行性实验

日期：2026-11-05。基于 `5267efd` 和前轮首页修复，原 release 程序，没有改产品代码。

## 结论

**空会话的个位数 MiB RSS 已在当前完整程序上复现。** 使用 Linux `madvise(MADV_DONTNEED)` 回收主程序的只读文件映射后，空闲 RSS 从约 27.4 MiB 降至 7.3 MiB。无需删掉模型、工具、Web 或其他功能。

但这并不等于“所有功能活跃时都只需要 7 MiB”：输入会重新触碰约 4 MiB 代码页，设置界面会触碰更多代码。维持低空闲 RSS 与降低活跃工作集是两种不同工作。

## 方法

- 使用前轮保存的原始 release 二进制，隔离 MOC_HOME、工作目录和会话目录。
- 120×40 真实 PTY，每种模式独立启动三次，报告中位数。
- 对照组不加载探针；实验组通过 LD_PRELOAD 启动一个诊断线程，收到 SIGUSR2 后用 `dl_iterate_phdr` 识别主可执行文件。
- 仅对主程序不含 PF_W 标记的 PT_LOAD 完整文件页调用 `madvise(MADV_DONTNEED)`。保留所有可写段，包括 RELRO 所在可写加载段；保留堆、栈、业务数据及共享库。
- 内存取 `/proc/PID/smaps`，缺页及 CPU 取 `/proc/PID/stat`；输入延迟从写入 PTY 到剥离 ANSI 后匹配到回显。
- 顺序：界面就绪 → 回收 → 空闲 3 秒 → 10 次输入/清空 → 打开设置并 Tab 操作 → 帮助/退出 → 空闲 3 秒 → 再次回收。
- ANSI 输出检查确认包含设置、供应商、模型等实际界面内容，进程正常退出。
- 不发送模型请求，不改变系统 swap、page cache、内核参数，也没有对真实用户进程操作。

## 实测结果

| 时刻 | 未干预 RSS MiB | 回收只读页 RSS MiB | 回收 + 单 Tokio worker RSS MiB |
|---|---:|---:|---:|
| 启动完成，尚未回收 | 27.30 | 27.41 | 26.88 |
| 回收后 100 ms | 27.30 | 7.31 | 6.68 |
| 继续空闲 3 秒 | 27.30 | 7.31 | 6.68 |
| 连续输入后 | 27.30 | 11.05 | 10.66 |
| 打开设置后 | 28.90 | 20.74 | 19.75 |
| 交互结束，空闲 3 秒 | 28.97 | 21.12 | 19.98 |
| 再次回收后 | — | 8.59 | 7.60 |

回收后空闲 PSS 分别约 5.02 MiB、4.34 MiB。PSS 与 RSS 的不同主要来自共享库分摊，不能拿 PSS 对比原来的 RSS。

输入成本：

| 指标 | 未干预 | 回收只读页 |
|---|---:|---:|
| 第一轮输入回显中位数 | 17.80 ms | 18.10 ms |
| 全部输入回显中位数 | 17.82 ms | 17.80 ms |
| 输入阶段新增 minor faults | 0 | 62 |
| 输入阶段新增 major faults | 0 | 0 |
| 输入阶段累计 CPU 中位数 | 0.01 秒 | 0.01 秒 |

这只能说明当前机器、热文件缓存、少量交互下未观察到显著输入延迟劣化。没有测磁盘冷缓存、内存压力下重新读取、长时间频繁回收、完整设置操作及模型/工具工作负载，不承诺这些场景同样无成本。

## 这项实验到底省了什么

`MADV_DONTNEED` 保留虚拟地址及文件映射，撤去当前进程对应页的驻留映射；再次访问由内核缺页处理恢复内容。文件没有改，功能代码仍存在。

**不能把 RSS 减少 20 MiB 描述成系统物理内存立即减少 20 MiB。** 页可能仍存在于全局文件缓存中，供本进程或其他进程复用，也可在内存压力下回收。这不是堆结构压缩，更不是修改 RSS 统计；它确实降低进程驻留集合，但必须连同文件缓存及缺页成本一起解释。

该技巧更适合“启动结束后冷却”或长时间空闲时的选择性回收，而非每按一次键就把所有代码页扔掉。产品化需要定义空闲状态、冷页范围、触发间隔，并测试信号、卸载、并发及各平台差异。当前探针只是可行性实验，不应直接成为产品默认实现。

## 达到不同目标的路线

### 目标 A：刚启动/长期空闲时 5–10 MiB RSS

已有 6.7–8.6 MiB 实测证据，是现实目标。可结合：

1. 启动路径结束后的选择性文件页回收，优先 Linux；区分数据页和只读文件页。
2. 延迟初始化 HTTP/TLS、复杂配置编辑、工具 schema、插件/MCP 管理等冷功能；需要逐个测初始化触碰的代码页，不能只看堆分配。
3. 对终端尺寸和工作负载设置合理缓冲及线程策略。单 worker 本次只再省约 0.6 MiB，收益小且影响并发，不宜为了这个数字直接改默认。

空会话的稳定堆只有约 0.95 MiB，因此主要空间在“哪些代码页必须常驻”，不是更换分配器。

### 目标 B：持续输入、设置和常用功能也保持 5–10 MiB

有优化空间，尚未证明达标。当前实验中输入后 11.1 MiB、设置后 20.7 MiB，说明必须缩小常用路径跨越的代码页：

- **PGO/BOLT 热冷代码布局**：用真实启动、输入、滚动和设置工作负载采样，把经常一起执行的函数与基本块聚集；冷代码移开，减少代码页工作集。收益须用 RSS/缺页和延迟验证，不能用二进制体积代替。
- **LTO、codegen-units、opt-level=s/z 对照**：减少单态化/内联造成的体积和布局分散；体积与速度可能相互影响。未在本轮构建比较，不给出节省百分比。
- **缩短空界面初始化链路**：当前在进入前端前就构造 Core，并建立内嵌 RPC 连接及完整初始化流程；可拆出仅空界面需要的元信息，把执行设施推迟到首次使用。
- **真正的可选链接或按需模块**：当前 CLI 对 TUI、Web、ACP、PTC 都是直接依赖。拆分功能必须实际减少被触碰的代码与重定位，不能假设删掉文件大小就等比例减少 RSS。

### 目标 C：严格 2–5 MiB RSS

可作为轻量前端或启动壳的设计目标，目前没有全功能 moc 达到它的实测证据。更可靠的架构是：轻量 TUI 壳在空闲时独立运行，首次发消息/恢复历史/使用工具时再启动 Core。若要求单文件分发，可以讨论内嵌 payload 后按需启动，但要承担部署、版本、生命周期和 IPC 复杂度。

必须统计完整进程树：不能让 TUI 显示 3 MiB，同时把几十 MiB 偷藏到常驻后端中。只有 Core 尚未启动或真正退出时，总空闲成本才可能符合目标；Core 活跃后的总内存仍要如实记录。

不推荐以强制 swap、频繁工作集清空、压缩壳解压到匿名内存等办法追求漂亮 RSS。这些做法可能转移开销、增加延迟，或破坏文件页共享/回收优势。也没有证据认为改为 WASM/JIT 或另一种语言会自然更省。

## 对 moc 的建议

先将成功标准定为：**空会话静置后 RSS <10 MiB，连续输入保持低延迟，内存压力下恢复不卡顿；同时报告 PSS、匿名页、文件页和缺页次数。** 先实现启动链路瘦身与选择性冷页回收，再做真实 PGO/BOLT/LTO 对照。只有确实要求 <5 MiB 且愿意接受延迟启动后端，才升级为轻前端/按需 Core 架构。

本轮没有实现这些产品改动；附件包含 C 探针、PTY 脚本、全部三次 JSON/smaps/ANSI 和汇总结果。测试进程均已退出。
