# moc 启动与运行时内存优化（2026-11-05）

## 本轮交付

基于提交 `5267efd`，保留前轮 Web 首页修复和依赖 feature 裁剪。在不改变默认 codegen 并行度、不启用 LTO、不裁掉用户功能的前提下，实施四项优化：

1. 默认 LLM HTTP/TLS 客户端首次请求时初始化。
2. Linux TUI 在静置后有限次回收主可执行文件的只读文件页。
3. Web 资源逐文件预压缩，避免整包解码正文与响应压缩缓存常驻。
4. 压缩历史的归档描述符紧凑化，解析缓存仅首次借用时分配。

本轮未调用模型供应商，不读取真实会话，未提交 Git commit。

## 修改说明与行为边界

### 默认 HTTP/TLS 延迟初始化

默认 `Client::new()` 只保存配置和共享初始化槽，首次请求才创建 reqwest/TLS 连接池。多个 clone 共用同一个初始化结果和连接池；provider 自定义连接时限仍按原逻辑分池。

显式 `ClientBuilder::build()` 仍立即构建并返回配置错误，例如非法 User-Agent 不被推迟。默认初始化失败在首次请求时返回 LlmError，并记住该失败结果；原先默认构造失败会 panic，现在不会让空界面提前失败。

单项对照的空会话 RSS 中位数：**27.45 → 25.04 MiB**。这是启动时减少初始化与代码页触碰的收益，不是代码页回收带来的数值。

代码：[客户端](../crates/moc-llm/src/client.rs)。

### Linux TUI 空闲代码页回收

首次完成绘制并静置约 2 秒后执行一次；再次交互后静置至少 30 秒，且两次回收至少间隔 60 秒。执行后取消该空闲期限，继续阻塞在事件上，不增加周期轮询。提示、压缩进度、待绘制内容、跑马灯期间不安排回收。

只选主可执行文件加载头里 **PT_LOAD 且无 PF_W** 的完整文件页，通过 `MADV_DONTNEED` 让内核撤去当前驻留映射。保留映射地址，后续访问重新缺页。可写段（包括 RELRO 所在加载段）、匿名尾部、堆、线程栈和会话数据均不处理。代码中的少量 unsafe 集中在 moc-core，TUI/LLM 原有 `forbid(unsafe_code)` 不变。

检测到 ptrace 调试器时跳过，以免丢弃调试器写入只读映射的断点；读取不到 proc 状态也跳过。其他平台不启用该回收，不引入轮询。平台行为未在 Windows/macOS 实测。

**RSS 下降不等于全系统立即释放同等物理内存。** 文件页可能仍在系统页缓存中，可以复用，也可以在压力下被回收。重新进入设置/工具等路径会让 RSS 回升。它减少进程驻留工作集，不压缩业务堆。

代码：[回收与调度](../crates/moc-core/src/memory.rs)、[TUI 事件循环](../crates/moc-tui/src/event.rs)。

### Web 静态资源不再整包常驻

构建阶段把每个文件压成独立标准 zstd 帧，生成只读索引；小于 1 KiB 或压缩不划算的文件直接嵌入原字节。

支持 zstd 的请求直接借用嵌入帧；不支持时只解压当前资源，响应体拥有数据，传输完成即可释放。没有长期缓存整包正文，也没有运行时逐资源压缩缓存。保持 URL、MIME、SPA 回退、404、缓存头和 `Accept-Encoding` 协商行为。

代价：相比跨文件整包压缩，整个最终二进制从 72,183,464 增至 72,953,032 bytes，增加约 **0.73 MiB（约 1.1%）**；不支持 zstd 的重复请求要重复解压单个资源。未更改压缩等级、默认编译优化参数或并行度。每个嵌入文件均与 Vite 原始产物逐字节校验。

代码：[构建脚本](../crates/moc-web/build.rs)、[资源表示](../crates/moc-web/src/assets.rs)、[响应](../crates/moc-web/src/lib.rs)。

### 冷归档描述符紧凑化

原 Archive 每条内联保存 OnceLock<Vec> 与两个 Vec ID 列表。现在解析缓存改成 `OnceLock<Box<Vec>>`，只有调用需要稳定借用的接口才分配 Vec 缓存；临时派生读取仍不保留解析结果。

调用 ID 和结果 ID 归档后不追加，合并为一个 `Box<[String]>` 和分界下标；两类内部顺序不变，空普通文本不分配 ID 元素。保留 Arc 正文共享、cold_clone、写时复制、协议 JSON 形状及工具关联语义。缓存权重按新结构实际尺寸计入，而不继续使用旧常量。

10 万条定期压缩场景匿名 RSS 从 **107.29 → 102.65 MiB**，少约 **4.64 MiB**；这是业务数据结构的实际降低，与代码页回收分开。

代码：[正文共享/归档](../crates/moc-llm/src/content.rs)。

## 测量方法

- Ryzen 5 5600 / WSL2 / Linux；复用前轮已校验的合成日志，默认模型指向不可用回环地址，不发模型请求。
- 原始基线、仅延迟 HTTP、中间候选和最终构建均复制为独立文件，避免构建期间覆盖正在测的程序。
- TUI 120×40 真实 PTY，按尾部唯一标记确认实际正文就绪；静置 4 秒取样，随后输入 5 次并打开设置。每个主场景三次，中位数。
- smaps_rollup 记录 RSS/PSS/Anonymous，stat 记录 CPU 和缺页。VmHWM 与 smaps 读取时刻/内核 RSS 计数细节不同，少量差值不做过度解读。
- 启动时间含约 2.3 秒 PTY 无终端协商响应的固定等待，不等于普通终端体验。
- 共享机器后台负载和页缓存会影响时延。没有 flush 系统页缓存，没有做高内存压力试验；零 major fault 仅代表本次环境。

## TUI 前后结果

最终构建每场景三次中位数：

| 场景 | 就绪时 RSS：前 → 后 MiB | 静置后 RSS：前 → 后 MiB | 输入后 RSS：前 → 后 MiB | 匿名 RSS：前 → 后 MiB |
|---|---:|---:|---:|---:|
| 空会话 | 27.45 → 26.96 | **27.45 → 7.81** | 27.45 → 11.52 | 4.51 → 3.86 |
| 100 条 | 34.09 → 34.41 | **34.09 → 11.96** | 34.09 → 15.76 | 8.12 → 7.99 |
| 10 万条未压缩 | 345.52 → 344.20 | **345.52 → 321.65** | 345.52 → 325.54 | 319.40 → 317.62 |
| 10 万条定期压缩 | 133.64 → 129.29 | **133.64 → 106.79** | 133.64 → 110.35 | 107.29 → 102.65 |
| 单条 8 MiB Markdown | 158.18 → 156.18 | **158.18 → 133.54** | 158.19 → 137.20 | 131.65 → 129.72 |

不能将空闲数字当作启动峰值：最终版空会话首次显示约 27 MiB，2 秒静置后才降至个位数；巨型消息的解析树和排版峰值仍在。同一最终构建另一次空会话就绪 RSS 约 29 MiB、静置后约 8.05 MiB，最终全场景轮次为 26.96/7.81 MiB；没有把波动隐藏成“启动峰值稳定减少”。仅延迟 HTTP 的单项实验有收益，完整程序的文件页布局、预读和运行波动会影响最终启动 RSS。

最终输入回显中位数约 **17.70–17.94ms**，基线约 **17.89–18.26ms**；这个小幅差异不宣称提速。回收后输入产生约 **48–52 次 minor fault**，基线约 0–1 次，本次 major fault 为 0。不宣称冷磁盘或内存压力下同样没有恢复成本。

启动到就绪：空会话约 2.32/2.29 秒，100 条约 2.33/2.31 秒，未压缩 10 万条约 3.40/3.23 秒，定期压缩约 4.24/3.56 秒。巨型回复该轮基线约 6.04 秒、最终约 3.74 秒，但此前正常基线也曾约 3.6–3.9 秒，不能把这个波动宣称为算法提速。

## Rust Web 后端前后结果

此表不包含 Chromium。独立启动三次，先仅监听，再请求首页，最后请求首页引用的入口 JS/CSS 等资源；每种资源分别请求 zstd 和 identity 表示。

| 阶段 | 基线 RSS MiB | 优化 RSS MiB |
|---|---:|---:|
| 仅监听 | 17.43 | 17.85 |
| 请求首页后 | 38.78 | 20.97 |
| 请求入口资源后 | **41.69** | **23.13** |

首页请求时间中位数约 **44.24 → 1.24ms**，主要因为不再首先解压整包。加载入口资源后的匿名内存由约 **21.71 MiB 降至 2.80 MiB**，符合取消资源缓存的归因。仅监听阶段匿名内存也下降，但文件代码页布局波动抵消了其 RSS 收益，不声称这一步 RSS 已减少。

另用真实 Chromium 打开生产页面：会话列表、100 条历史及末尾标记完整，代码块渲染成功，无资源 HTTP 错误或页面异常。屏外 `content-visibility` 会影响 innerText，因此用 textContent 核验末尾消息，并未把不可见文本当作加载失败。

## 验证与剩余空间

- LLM 单元测试 134 项（随后新增混合 ID 用例独立通过），LLM 集成测试全部通过，覆盖真实本地 HTTP 请求、流式输出和超时配置。
- 会话回放/分页/回退/前滚/压缩等 41 项通过；空闲调度/页边界 2 项通过。
- TUI 全部 418 项通过；Web 6 项通过，包含每个嵌入资源与原始字节对照和编码协商。
- 最终 release 构建通过，默认编译参数和并行度保持原状。

本轮没有重写两套历史 Entry/TranscriptEntry 存储，也没有把巨型单条 Markdown 改为块内虚拟排版。它们仍是运行时堆的大头；本次对照中未压缩 10 万条匿名 RSS 基本不变，直接证明仍有这些成本。浏览器的 DOM 历史保留也未在本轮修改。没有用静默截断正文、删除功能或修改持久化格式换内存。

最终一分钟冷却验证：启动后第 6 秒 RSS 7.95 MiB，输入后第 10 秒 12.36 MiB，30/60 秒约 12.55 MiB，第 68/75 秒约 8.14 MiB。输入内容完整，78 秒进程 CPU 累计约 0.04 秒，major fault 为 0。证明单段空闲一次、交互重新计时和一分钟冷却行为生效。

回收按加载段属性限制范围，并不逐页识别冷热；热页下次访问仍会重新进入 RSS，这是额外 minor fault 的来源。最终原始结果见附件的 `idle-cooldown.json`、`results-final.json`、`web-final.json`。
