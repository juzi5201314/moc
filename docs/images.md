# 图片发送与请求体诊断

无论你通过终端剪贴板粘贴、Web 拖拽上传、`@图片路径` 引用、编辑器 ACP 传入，还是 MCP/工具返回内联图片，在发往模型接口前都会经过统一的图片预处理。恢复历史会话时同样走这套规则。

预处理只作用于即将发出的请求副本，**不会改写或删掉会话里保存的原始图片**；`/context` 面板展示的也是实际发送版本。

## 单图预处理规则

- **格式校验**：支持 PNG、JPEG、GIF、WebP、BMP，按文件真实格式解码（不轻信后缀或 MIME）。
- **输入上限**：单张原始图片不超过 20 MiB、总像素不超过 6,400 万；损坏或超限图片会在本地直接报错，不会带病发给上游。
- **比例与尺寸**：自动校正拍摄方向、保持纵横比、绝不放大小图；单图默认按总像素 `1568 × 1568`、最长边 `8192 px` 为上限缩放（避免长截图仅因单边过长把文字压糊）。
- **自适应编码**：单图默认目标体积为 500 KiB。尺寸合规且体积已足够小（不超过当前预算与 125 KiB 的较小值）时直接保留原图；否则对比 PNG 与 JPEG（质量 85 → 75 → 60）择优；含真实透明通道的图片对比 PNG 与无损 WebP，不丢透明度。
- **二次缩放与兜底**：仍超预算时按 85%、70% 边长继续压缩；若触及清晰度下限依然装不下，会在本地直接报错，建议裁剪关键区域或分批发送。
- **结果缓存**：按图片内容摘要与体积目标缓存最近 32 份结果（上限 24 MiB），避免每轮对话重复压缩，也绝不会对有损副本反复二次压缩。
- **远端图片链接**：`http(s)://` 图片链接原样传递，不由本地下载，不占用内联字节预算；`data:…;base64,…` 链接则与本地图片同等处理。

## 多图与历史图片预算

每轮请求发往模型前，会统筹计算**本轮图片、历史对话图片、工具返回图片以及重复出现的图片**：

1. 先按单图规则完成初压，再编码完整请求并扣除文本、工具定义与协议封装占用的字节。
2. 所有内联图片编码后的总上限为 **8 MiB**，且不能超出请求剩余空间；优先满足小图，再把剩余额度平分给大图。
3. 需要进一步压小时，始终从原始图片重新编码，**绝不静默删掉历史或当前图片**。
4. 发出前按最终 HTTP 请求体的精确字节数再做一次校验；仍超限则本地中止，不浪费网络请求。

默认整份请求体上限为 **50 MiB**。如果你的代理或模型网关限制更严格，可在对应模型配置中调小 `max_request_bytes`：

```toml
[providers.my-provider.models.my-model]
max_request_bytes = 2097152 # 整份请求上限 2 MiB（含对话文本、工具定义与全部图片）
```

> 正常的上下文压缩可能会按摘要策略归档历史图片；这与发送前因请求体积超限而静默丢图是两回事。

## 413、524 与请求诊断

常见 HTTP 状态码的中文解释与自动重试策略见 [上游错误与自动重试](http-errors.md)。

当上游返回 HTTP 错误时，错误详情会自动附带以下诊断信息：

- 最终请求体大小与本地配置的上限；
- 内联图片总数、其中历史图片数、远端 URL 图片数；
- 图片压缩前后的总字节数、非图片内容所占字节数；
- 等待耗时、上游请求 ID，以及 Cloudflare `cf-ray`（若响应包含）。

排查重点：

- **HTTP 413**：上游明确拒绝了当前请求体积。请按网关实际限制调小该模型的 `max_request_bytes`，或裁剪图片、压缩历史上下文。
- **HTTP 524**：Cloudflare 的超时状态码，并非图片专属错误，也不直接代表请求体超限（常见原因包括上游响应超过读取超时，或写入上游超过写超时）。带图与不带图的 524 统一按超时重试策略处理，绝不会为了重试自动删图；请结合等待耗时、请求体积与上游日志综合排查。
