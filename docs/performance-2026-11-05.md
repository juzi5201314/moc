# moc 性能调研（2026-11-05）

测量对象：提交 `5267efd48fa4cba11eca0865e98a817842caf663`，本机 release 构建。WebUI 另包含本次发现的首页无限重渲染修复；原始提交的生产页面在空会话下也会触发 React #185，不能作为正常运行的性能基线。

## 测量方法与环境

- AMD Ryzen 5 5600，6 核 12 线程；Linux 6.18.54.1-microsoft-standard-WSL2；约 19.3 GiB 内存。共享开发机器，未关闭用户其他服务。
- rustc 1.101.0-nightly（8006091eb，2026-10-17）；HeadlessChrome 147.0.0.0；Node 26.12.0；agent-browser 0.20.14。
- `cargo build --release --bin moc`；生产前端由构建脚本打包嵌入。未使用 dev 构建性能数据。
- 隔离 `MOC_HOME`、会话目录与工作目录；虚拟模型指向回环不可用端口，整个测试不发送模型请求。关闭 MCP、插件和 skills。
- TUI 通过 120×40 PTY 启动，直接观察真实界面输出。WebUI 使用独立 Chromium 会话，1440×1000，访问隔离 moc 服务。
- 各场景独立启动三次，报告中位数。TUI 每约 25ms、Web 每 100ms 采集 `/proc` 的 RSS 和 CPU 累计时间。TUI 额外记录内核 VmHWM。
- CPU 百分比以一个逻辑核满载为 100%；空闲窗口约 3–4 秒，CPU 时间分辨率 10ms，0% 只能表示窗口内几乎没有可测 CPU 消耗。
- 浏览器使用 CDP 读取 JS 堆、主线程任务时间、长任务、DOM 数；PSS 是专用浏览器进程集合的比例驻留集，包含浏览器本体、renderer、GPU 等；RSS 求和会重复计算共享页。JS 堆不能代表浏览器总内存。
- 所谓“首次打开”是新 moc 进程及新页面内首次打开该会话；没有清除操作系统页缓存，不等同物理磁盘冷启动。浏览器重复试验清除测试 origin 的持久标签及 HTTP 缓存，浏览器主进程复用。

## 语料

用户与助手交替，普通消息约 2 KiB，含中文、Markdown 标题、短 Rust 代码块；消息尾部带唯一标记，用于验证实际加载。合成内容不是用户真实会话。

| 场景 | 消息数 | JSONL 大小 | 说明 |
|---|---:|---:|---|
| 空会话 | 0 | 0 | TUI 新会话；Web 欢迎页草稿 |
| 小会话 | 100 | 0.218 MiB | 未压缩 |
| 大会话 | 10,000 | 21.764 MiB | 未压缩 |
| 巨大会话 | 100,000 | 217.544 MiB | 未压缩，超过正常模型上下文容量的压力场景 |
| 定期压缩巨大会话 | 100,000 | 217.572 MiB | 每 1,000 条写一个 soft checkpoint，保留最近 20 条 |
| 单条超长回复 | 100 | 8.661 MiB | 最后一条助手回复约 8 MiB |

## TUI 实测

RSS 为界面就绪后的空闲中位数；峰值为三次 VmHWM 的中位数。CPU 秒为一次完整测量过程的累计 CPU 时间，包含打开、空闲、输入与按键探测。

| 场景 | 空闲 RSS MiB | 峰值 MiB | 启动到正文 ms | 累计 CPU 秒 | 输入回显 ms |
|---|---:|---:|---:|---:|---:|
| 空会话 | 27.82 | 28.00 | 2300.92 | 0.07 | 16.99 |
| 100 条 | 34.82 | 35.01 | 2298.15 | 0.09 | 18.01 |
| 1 万条 | 65.75 | 65.94 | 2396.61 | 0.16 | 17.85 |
| 10 万条，未压缩 | 344.84 | 346.13 | 3206.29 | 0.99 | 18.10 |
| 10 万条，定期压缩 | 134.45 | 134.63 | 3509.56 | 1.30 | 18.03 |
| 单条 8 MiB 回复 | 157.08 | 166.77 | 3635.23 | 1.42 | 17.82 |

所有场景空闲 CPU 中位数均为 0%；单次最高约 0.33%，受 10ms 采样粒度影响。进程稳定为 14 个线程。

**启动计时边界**：测试 PTY 不回答终端能力查询，包含约 2.3 秒固定等待，其中键盘协商明确允许最多 2 秒超时。不能据此声称普通终端每次启动都需 2.3 秒。相对空会话，10 万条未压缩增加约 0.91 秒，定期压缩增加约 1.21 秒。输入回显约 18ms 与 TUI 的 16ms 帧预算一致。

**解释**：定期压缩场景比未压缩少约 61% RSS，但冷打开多约 0.30 秒，符合回放时冻结历史正文需要额外序列化、文件写入和映射的行为。单条 8 MiB 的回复导致约 157 MiB 驻留，即使总文件仅 8.7 MiB，说明消息形状与渲染中间结构同样重要；这不是只按文件大小即可预测的开销。

## WebUI 实测

下表为三次中位数。浏览器 PSS 在首屏就绪后约 1.5 秒取样，包含专用 Chromium 的公共进程成本；后端 RSS 与浏览器 PSS 是不同口径，不建议直接相加当成精确总量。打开时间从点击会话按钮到对话 DOM 存在且经过两次动画帧；不等于所有异步高亮、布局与自动滚动都已结束。

| 场景 | 后端 RSS MiB | 浏览器 PSS MiB | JS 堆 MiB | 点击到显示 ms | DOM 元素数 |
|---|---:|---:|---:|---:|---:|
| 空欢迎页 | 47.37 | 435.95 | 10.58 | — | 168 |
| 100 条 | 51.46 | 563.29 | 30.17 | 756.57 | 15,699 |
| 1 万条 | 82.88 | 560.87 | 53.27 | 1651.11 | 25,000 |
| 10 万条，未压缩 | 358.18 | 577.35 | 54.04 | 1897.90 | 24,920 |
| 10 万条，定期压缩 | 152.32 | 623.53 | 40.64 | 2549.42 | 24,920 |
| 单条 8 MiB 回复 | 74.67 | 581.51 | 50.98 | 1290.85 | 24,506 |

页面导航到会话列表可用约 245–347ms；隔离 HTTP 服务启动至可请求约 86–94ms。这里的首页响应经过当前机器页缓存，不能当作硬盘冷启动时间。

Web 默认按 64 KiB 投影单消息，8 MiB 回复没有完整进入浏览器；TUI 使用完整消息。因此这一行 Web 更低的内存并不表示它完整呈现同样的 8 MiB 正文。

### 连续翻页

首屏后点击“加载更早的消息”10 次。自动顶部观察器也可能预取，因此首次显示后的实际轮次数不保证恰好 40；原始 RPC 保留了返回条数。测量总时间包含脚本约 1 秒翻页间隔和最后 1.5 秒稳定等待。

| 场景 | 浏览器 PSS：打开后 → 翻页后 MiB | JS 堆：打开后 → 翻页后 MiB | DOM：打开后 → 翻页后 | 翻页阶段浏览器 CPU 秒 | 阶段耗时秒 |
|---|---:|---:|---:|---:|---:|
| 1 万条 | 560.87 → 889.31 | 53.27 → 233.88 | 25,000 → 149,000 | 9.20 | 8.85 |
| 10 万条，未压缩 | 577.35 → 891.19 | 54.04 → 232.96 | 24,920 → 148,520 | 8.55 | 8.59 |
| 10 万条，定期压缩 | 623.53 → 880.46 | 40.64 → 225.62 | 24,920 → 148,520 | 8.70 | 8.62 |

这几个场景的后端 RSS 在翻页期间基本不变，CPU 只增加约 0.02 秒。前端渲染与对象保留是翻页时更明显的成本。合成 Markdown 每条含重复代码块，DOM 密度较高，数字不适用于纯短文本聊天。

补充一次 10 万条场景：翻页及滚动结束后静置，再强制 GC，浏览器 PSS 从约 837.49 MiB 降至 712.95 MiB，JS 堆从 232.02 MiB 降至 180.52 MiB，DOM 仍为 148,524。部分增长是待回收垃圾，另有大量对象及 DOM 被正常持有；没有证据把它称为泄漏。

### CPU 与交互

- Rust Web 后端在各场景 4 秒空闲窗口内 CPU 中位数均为 0%。
- 首屏后短空闲窗口的浏览器全进程 CPU 中位数：空页 0.77%，100 条 12.28%，1 万条 9.74%，10 万条 8.19%，定期压缩 1.25%，单条超长 9.45%。这是首屏后的短时间窗口，包含延迟渲染/GC/浏览器内部工作，不能视为长期静态空闲功耗。
- 补充静置试验的 5 秒前后快照，存活浏览器进程 CPU 增加约 0.55 秒（约 11% 单核），主线程 TaskDuration 增加约 0.327 秒；JS CPU profile 的 4,578 个采样中 4,564 个为 idle，ScriptDuration 和 LayoutDuration 没有可测增量。这不足以把剩余 CPU 归因于 React 重渲染；进一步分析需要浏览器 native trace。补充试验的原始 settled_idle 标签还包含 profiler 停止和 GC，不能用整个标签区间估算稳定空闲 CPU。
- 在已加载内容中滚动，2 秒 requestAnimationFrame 采样的 P95 帧间隔为 16.7–16.8ms；该测试没有持续翻页到历史开头，不能证明所有滚动场景流畅。
- 10 万条翻页后的真实 CDP 输入到两次动画帧约 28.82ms，单次补充数据。
- 各场景一次运行的最大长任务，取三次中位数：100 条 573ms、1 万条 868ms、10 万条 674ms、定期压缩 672ms、单条超长 1171ms。翻页/初次 Markdown 渲染期间存在明显长任务，即使随后滚动帧间隔正常。

### 独立后端 RPC

浏览器 CDP 的网络事件回调可能受页面主线程阻塞影响，不能把其事件间隔直接当成纯后端处理耗时。另用 Node 原生 WebSocket 连独立 moc 服务，采用相同的 `session/load`、80 条 / 64 KiB `session/history` 和 `session/context` 请求，每场景独立启动三次：

| 场景 | 首次 session/load ms | 每页 session/history ms | session/context ms |
|---|---:|---:|---:|
| 100 条 | 5.19 | 4.40 | 7.79 |
| 1 万条 | 92.57 | 3.94 | 10.83 |
| 10 万条，未压缩 | 902.07 | 3.29 | 40.71 |
| 10 万条，定期压缩 | 1311.54 | 4.21 | 5.80 |
| 单条 8 MiB 回复 | 29.19 | 3.05 | 5.25 |

首次加载随完整历史规模增长；加载后分页速度没有随 1 万到 10 万条明显变慢。压缩使上下文统计及常驻内存更小，但冻结归档让首次回放更慢。

## 代码依据

- Core 首次打开通过 `SessionTable::get` 调用完整 `read_state` 回放；分页降低传输和显示成本，并不让 Core 的会话状态完全按需从磁盘读取。[会话加载](../crates/moc-core/src/session/mod.rs#L245)、[流式回放](../crates/moc-core/src/session/store.rs#L618)。
- 失活正文冻结到私有只读 mmap，checkpoint 推进 context_start 后归档，因而定期压缩能降低 RSS。[归档实现](../crates/moc-core/src/session/archive.rs#L52)、[回放边界](../crates/moc-core/src/session/archive.rs#L150)。
- Web 每页 80 条、单消息预算 64 KiB；TUI 每页 64 条，但请求 `full_messages: true`。长消息场景二者显示语义不同，不能直接把内存差异全部归因于前端效率。[Web 加载](../crates/moc-web/web/src/store/lifecycle.ts#L30)、[TUI 加载](../crates/moc-tui/src/event.rs#L210)、[页面预算分支](../crates/moc-core/src/session/mod.rs#L629)。
- Web 将新读入历史持续 prepend 到 blocks，已加载轮次全部挂载，`content-visibility: auto` 可跳过屏外布局/绘制，但不是卸载 DOM。[历史追加](../crates/moc-web/web/src/store/lifecycle.ts#L204)、[全部轮次挂载](../crates/moc-web/web/src/components/chat/chat-thread.tsx#L140)、[屏外渲染策略](../crates/moc-web/web/src/components/chat/chat-thread.tsx#L237)。
- Core 只读缓存回收限额为 4 个、64 MiB，但跳过 pinned/在途引用；不是整个进程硬内存限制。[缓存回收](../crates/moc-core/src/session/mod.rs#L288)。
- TUI 能力协商超时与 16ms 帧预算：[终端协商](../crates/moc-tui/src/terminal.rs#L44)、[事件循环](../crates/moc-tui/src/event.rs#L921)。

## 本次修复与验证

`WorkflowNavRow` 直接订阅一个每次返回新对象的 Zustand selector，造成 getSnapshot 不稳定、无限重渲染和首页空白。以项目已有 `useShallow` 模式稳定订阅返回值，未改变徽标含义或功能。

新增真实侧栏挂载回归测试：修复前复现 Maximum update depth exceeded，修复后正常挂载，并验证运行中的 workflow 徽标随 store 更新。最终前端 19 个测试文件、100 个测试全部通过（5.74 秒）；类型检查、限定文件格式检查及 release 构建通过。既有 Markdown 组件测试有非阻断的 React act 警告，未影响测试结果。

## 建议的优化顺序

1. **优先处理 Web 已加载历史的渲染和保留规模。** 10 页就产生约 14.9 万 DOM 元素、约 230 MiB JS 堆，并消耗约 8.5–9.2 CPU 秒。可验证的下一步是轮次窗口化、屏外 Markdown 延迟解析及已读历史的有界保留；应同时保证选择复制、滚动锚点和回退定位正确。`content-visibility` 已有收益，但不能解决对象与 DOM 数量。
2. **单独处理 TUI 单条巨型 Markdown。** 8 MiB 回复让 RSS 约 157 MiB，首次完整显示增加约 1.33 秒。下一步宜采样完整消息传输、Markdown 解析和折行缓存，确认占比后再选分块或增量结构。本次没有分配器级 profile，不能断言哪一种结构占用了全部内存。
3. **优化 Core 首次回放需要保持持久化语义。** 10 万条冷进程首次加载约 0.90 秒，定期压缩约 1.31 秒；分页仅 3–4ms，继续微调分页不是最大收益点。若目标是超大历史快速恢复，可研究可校验的持久索引/状态 checkpoint，仍必须识别跨进程追加、截断和版本变化。
4. **保留正文归档策略。** 同样 10 万条，TUI RSS 从 344.84 降至 134.45 MiB，Web 后端从 358.18 降至 152.32 MiB；代价是首次加载增加。应按“首次打开速度 vs 常驻内存”明确权衡，不能只报其中一个指标。

本次仅修复阻断测试的首页崩溃，没有实施上述性能优化，也没有据合成基准承诺收益倍数。

## 复现与原始数据

附件包含 `generate.py`、`tui_bench.py`、`web_bench.mjs`、`rpc_bench.mjs`、`summarize.py`，以及各次采样 JSON 和浏览器空闲 CPU profile。脚本里的 ROOT/BIN 默认指向本机测试目录与当前仓库；换机器时先改这两个路径。

```bash
cargo build --release --bin moc
python /tmp/moc-perf-20261105/generate.py
agent-browser --session moc-perf open about:blank
python /tmp/moc-perf-20261105/tui_bench.py --repeat 3
node /tmp/moc-perf-20261105/web_bench.mjs empty,small,large,huge,compact,wide 3
node /tmp/moc-perf-20261105/rpc_bench.mjs
MOC_PERF_DEEP=1 node /tmp/moc-perf-20261105/web_bench.mjs huge 1
python /tmp/moc-perf-20261105/summarize.py
agent-browser --session moc-perf close
```

测量过程中先后纠正了合成角色枚举大小写、CSS 选择器转义和浏览器持久标签自动恢复的测量干扰。正式结果仅采用修正后的成功运行，TUI 和 Web 均为每场景三次；补充 GC/profile 试验为一次。原始结果中的浏览器 RPC 时间用于排查事件链路，纯后端延迟请使用独立 `rpc-results.json`。

## 范围与局限

- 未测真实模型流式生成、工具执行、MCP/插件宿主、图片、多会话并发或几千个会话的侧栏；这些开销不能从本报告外推。
- 未做长时间泄漏测试，连续翻页导致的保留不等同于内存泄漏。
- 基准脚本与原始 JSON 作为独立附件保留；生成器可以重建语料，不需要分发约 475 MiB 的合成日志。
