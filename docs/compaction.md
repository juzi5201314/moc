# 上下文压缩

长对话接近模型窗口上限或你手动执行 `/compact` 时，moc 会对历史进行压缩，同时把完整原文归档到会话历史空间（模型可按需通过 `read history://compaction/INDEX.md` 回查）。

目前内置三种压缩算法，可在「设置 → 上下文」或配置文件 `[compaction].method` 中选择：

- **`moc`（默认）**：先做本地轻量修剪（裁剪旧工具输出等），空间仍不足时再调用模型生成检查点摘要，并保留最近一段完整历史。
- **`grok_build`**：九段式结构化摘要，配合最近用户原话回放。
- **`eocc`（实验性）**：直接以“任务原文 + 六段交接状态”替代旧历史，详见下文。

## 默认算法（`moc`）的工作原则

### 信息优先级与事实验证

- **用户最新要求优先**：较新的真实用户指令优先于旧摘要和模型推断；同一个提问以最新有效回答为准。
- **区分来源与验证状态**：压缩提示明确标注来源，不会把普通汇报、引用或工具输出误当成用户拍板的决策；同时区分“已通过验证的状态”与“后续尚未验证的改动”。
- **关键事实核对**：系统会从对话正文和文件工具参数中提取关键路径、标识符与数值，校验候选摘要是否漏掉用户要求或重要锚点（不会拿大段代码正文或补丁行号凑数）。

### 近期历史保留边界

`keep_recent_tokens` 控制压缩后保留在尾部的近期对话预算，但遵循完整的消息边界：

- 工具调用与对应的全部结果视为不可拆分的整体，绝不会把成对的调用与结果拆散。
- 即使设为 `keep_recent_tokens = 0`（纯摘要），尚未收到结果的工具调用仍会保留。
- 如果你最近发出的那条真实消息已被移出保留尾部，系统会从原始日志把它单独摘录回放（超长输入保留首尾共最多 4,096 估算 token 并标明省略处），避免压缩后“忘记刚说的话”。
- 压缩后的总上下文还包括系统提示、工具定义、摘要本身与用户摘录，因此 `keep_recent_tokens` 不是压缩后总用量的硬上限。

需要观察压缩细节时，可设置 `RUST_LOG=moc_core::compact::soft=debug` 查看估算 token、候选校验结果与重试次数（属本地诊断，不替代上游实际计费）。

## EoCC：实验性交接状态

受 NVIDIA 论文 [《You don’t need long context》](https://arxiv.org/abs/2611.05306) 启发，适合希望在较短工作窗口内推进多步骤任务的场景。

### 工作方式

- **不保留普通尾部**：不做轻量修剪，也不按 `keep_recent_tokens` 保留旧轮次（仅保留尚未收齐结果的在途工具组）。
- **确定性任务回放**：直接从原始日志提取本阶段首条与最新用户指令（超长按首尾摘录，单条最多 3,072、整块最多 8,192 估算 token），不靠模型反复转述以免走样。
- **六段交接简报**：摘要围绕“剩下要做什么”生成，包含六个固定章节：`Objective`（目标与完成条件）、`Established Facts`（后续所需事实）、`Applied Changes`（已做改动与验证状态）、`Verification`（已跑检查与当前障碍）、`Dead Ends`（已排除的死路）和 `Remaining Plan`（剩余步骤与立即下一步）。
- **失败不破坏历史**：简报正文上限 4,096 估算 token，格式或预算不达标时最多重试 3 次；若生成被截断、报错或重试耗尽，当前历史原样保留，绝不硬塞残缺摘要。

### 配置示例

在设置页的压缩算法中选择 `EoCC（实验性：交接状态）`，或在配置文件中写入：

```toml
[compaction]
method = "eocc"
# 如需配合固定短窗口阈值试验，可同时配置（请先用 /context 观察常驻开销再取值）：
# threshold = { mode = "tokens", value = 48000 }
```

### 使用注意

- 不同模型对短窗口交接的适应度差异较大，小模型或摘要能力较弱的模型在过紧的窗口下可能明显退步；请先用 `/context` 确认系统提示和工具定义本身的常驻开销，再决定阈值，不要直接照搬 16K 这类极小值。
- 更频繁的压缩会带来额外的摘要输出并降低提示缓存命中率，是否划算需要结合任务完成率与实际账单一起评估。
